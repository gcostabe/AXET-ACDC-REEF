0. TRÍADA DE FILTRADO: NIVEL DE SALTO, OPCIÓN Y MENÚ 
Cada invocación al motor de reglas de risk-selection se identifica de forma unívoca 
mediante tres coordenadas, que el orquestador externo envía como parámetros del 
RiskSelectionRequest y que el repositorio usa para filtrar las reglas aplicables en la 
colección RS-RULES-ACTIONS-CONDITIONS. 
La notación compacta usada en la documentación del orquestador es [processStep-
optionMenuNumber-optionNumber].

CÓMO FUNCIONA LA EVALUACIÓN DE CONDICIONES 
El sistema soporta dos versiones de evaluación de condiciones de reglas: V1 (Legacy) y V2 
(Expresiones Java). 
Routing Automático (RulesEvaluationRouter) 
El sistema decide automáticamente qué versión usar: 
Regla simple: Si en MongoDB la regla tiene el campo condition con valor, se usa V2. Si 
está vacío o no existe, se usa V1. 
 
VERSIÓN 1 (V1) - Condiciones Estructuradas 
Descripción 
V1 utiliza una estructura JSON en el campo ruleConditions para definir condiciones. Es el 
sistema original (legacy). 
Estructura en MongoDB 
Cada condición en ruleConditions es un objeto JSON con: 
{ 
  "factor": "insured.age",   // El fact a evaluar 
  "operator": "GE",         // Operador de comparación (EQ, NOT_EQ, GT, LT, GE
, LE, IN, NOT_IN, BTW, EX, NEX, BLANK) 
  "value": "18",            // Para operadores simples (EQ, GT, etc.) 
  "value1": "18",              // Para operadores BTW 
  "value2": "65",              // Para operadores BTW 
  "values": ["001","002"]      // Para operadores IN/NOT_IN 
}

Características V1 
Ventajas: 
● Estructura clara y predecible 
● Validación de esquema sencilla 
● Fácil de mantener para condiciones simples 
● No requiere conocimientos de programación 
Limitaciones: 
● Condiciones simples únicamente 
● No permite lógica compleja (OR anidados, cálculos, etc.) 
● Todas las condiciones se evalúan con AND implícito

EVALUACIÓN DE COLECCIONES CON PATRONES 
Introducción 
Tanto V1 como V2 soportan evaluación de reglas sobre colecciones (como beneficiarios, 
coberturas, asegurados) usando el operador/método ANY_MATCH. 
¿Cuándo usar ANY_MATCH?


--- [PÁGINA 22 DE 49] ---

Usa ANY_MATCH cuando necesites: 
●    Verificar si algún elemento de una colección cumple una condición

PRIORIZACIÓN DE REGLAS 
Introducción a la Priorización 
El sistema de priorización de reglas es un mecanismo que optimiza el procesamiento de 
reglas evitando redundancias cuando múltiples reglas afectan al mismo campo 
(processField). 
Objetivo principal: Una vez que se ha aplicado una regla a un processField específico, el 
sistema no procesará más reglas para ese mismo campo, mejorando el rendimiento y 
evitando resultados contradictorios. 
Cómo Funciona la Priorización 
Flujo de Evaluación: 
1. Carga de Reglas: El sistema obtiene todas las reglas aplicables del repositorio 
2. Cálculo de Prioridad: Cada regla recibe un score de prioridad basado en criterios 
específicos 
3. Ordenamiento: Las reglas se ordenan por prioridad descendente (mayor puntuación 
= ejecuta primero) 
4. Aplicación: Se ejecutan las reglas en orden de prioridad 
5. Bloqueo de Campo: Una vez se aplica una regla a un processField, ese campo queda 
marcado como procesado 
6. Filtrado: Las reglas subsecuentes que afecten a un processField ya procesado se 
saltan automáticamente 
Ventajas: 
   Rendimiento mejorado - No se ejecutan reglas innecesarias 
   Evita conflictos - Una única decisión por campo 
   Orden determinístico - Resultados predecibles y consistentes 
   Control granular - Prioridad explícita para cada regla
