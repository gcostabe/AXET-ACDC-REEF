PARTE II: ENDPOINT BATCH — ORQUESTADOR 
1. Endpoint 
Fichero: controller/OrchestratorController.java Caso de uso: 
usecase/ExecuteOrchestratorUsecase.java


--- [PÁGINA 5 DE 75] ---

Método Ruta Descripción 
POST /acdc/orchestrator/policies/execute Ejecuta el proceso E2E de 
cotización/emisión de póliza 
Es el único punto de entrada al flujo de orquestación completo. Recibe los datos de una 
póliza y coordina la cadena de servicios externos en orden estrictamente definido. 
 
2. Seguridad 
El endpoint está protegido con OAuth2 JWT (Spring Security Resource Server). Se requiere 
uno de estos roles de autoridad: 
@PreAuthorize("hasAnyAuthority('GAZU_ROLRTEMGR', 'GAZU_ROLRTEADM')") 
Situación Respuesta 
Sin token 401 Unauthorized 
Token válido pero sin rol 403 Forbidden 
Token válido con rol correcto Continúa el flujo 
La seguridad puede desactivarse con spring.security.enabled: false para entornos locales.

PARTE III: ENDPOINTS ONLINE 
Contexto 
A diferencia del orquestador batch que ejecuta el ciclo completo de una póliza de principio a 
fin, estos endpoints exponen operaciones granulares pensadas para ser invocadas desde 
frontales o BFF que necesitan ejecutar pasos concretos del proceso de contratación de forma 
individual y bajo demanda. 
Todos los endpoints comparten: 
● Base path: /acdc 
● Autenticación: OAuth2 JWT (Spring Security Resource Server) 
● Formato: application/json 
● Sistema fuente: SourceSystemEnum.ONLINE (frente al BATCH del orquestador)

PARTE IV: MOTOR DUP — REGLAS DE NEGOCIO 
1. ¿Qué es DUP?


--- [PÁGINA 18 DE 75] ---

DUP (Data Update Process) es el motor de reglas de negocio del sistema. Es un servicio 
externo que, dado el estado actual de una póliza y el identificador del paso en el que nos 
encontramos, devuelve un conjunto de reglas aplicadas (appliedRules) que pueden: 
● Asignar valores a atributos de la póliza (pre-cálculos, valores por defecto, herencia de 
datos). 
● Validar que los datos son correctos y coherentes (puede bloquear el flujo con 
errores). 
● Aplicar controles técnicos (reaseguro, cláusulas, impresión, opciones adicionales, 
etc.). 
El backend lo invoca a través de SelectRiskService → POST /risk-selection. 
 
2. Tipos de operación (DupOperationEnum) 
Valor Método en DupService Descripción 
PREVIOUS precalculateByStep() 
Pre-cálculo: aplica asignaciones sobre los 
atributos de la póliza en memoria. No bloquea 
ante errores de validación. 
VALIDATION validationByStep() 
Validación: aplica reglas que pueden devolver 
errores bloqueantes. Si hay errores, se lanza 
AcdcException. 
TECHNICAL_CONTROL processTCByStep() 
Control técnico: aplica reglas de control sobre 
coberturas, reaseguro, cláusulas, etc. Devuelve 
List<OPlyUtcP>.

ModulesService — Cálculo de módulos y paquetes de coberturas 
¿Qué es un módulo? 
Un módulo (o paquete) es una combinación predefinida de coberturas que el producto ofrece 
al asegurado. El servicio externo CalculatePackagesService es quien conoce qué paquetes 
son aplicables. 
El resultado de ModulesService.calculateModules() es una lista de OPlyPlyCDto, donde 
cada elemento representa una opción válida de cotización. 
Cuándo se calcula 
Se llama en la Fase 3 del orquestador, tras todos los controles técnicos y justo antes del bucle 
de coberturas.


--- [PÁGINA 57 DE 75] ---

Dos modos de cálculo 
La selección del modo es automática: se comprueba si todos los riesgos tienen 
NUM_SIMULACION. 
Condición Modo 
Todos los riesgos tienen NUM_SIMULACION Con simulación → 1 resultado 
Algún riesgo no tiene NUM_SIMULACION Sin simulación → N resultados 
Con simulación (NUM_SIMULACION informado) 
Para cada riesgo:  
  1. Lee NUM_SIMULACION → preferenceId  
  2. Llama a CalculatePackagesService (POST /calculate-packages)  
  3. Aplica las coberturas del paquete al riesgo  
  
→ Devuelve List con UN ÚNICO OPlyPlyCDto 
Sin simulación (primera cotización) 
1. Construye PackagesRequest con TODOS los riesgos  
2. Llama a CalculatePackagesService  
3. Extrae todos los preferenceId únicos  
4. Por cada preferenceId:  
   a. Clona el OPlyPlyCDto original  
   b. Para cada riesgo → aplica coberturas del paquete  
   c. Si todos ok → añade a la lista  
  
→ Devuelve List<OPlyPlyCDto> con N elementos

processRisk(...)

  ├─ Obtiene ResponseRisk

PARTE IX: SISTEMA DE AUDITORÍA 
1. Visión general 
El sistema registra de forma asíncrona y no intrusiva cada petición HTTP entrante y todas 
las llamadas WebClient salientes. 
Petición HTTP entrante  
  │  
  ▼  
AuditFilter  
  Inicializa AuditContext (ThreadLocal)  
  Captura URI, método, body req/res  
  │  
  ▼ (cada llamada WebClient)  
WebClientAuditInterceptor  
  Captura URL, body, status, duración  
  │  
  ▼  
AuditContext  
  Acumula hasta 30 WebClientCallInfo  
  │ al finalizar la petición HTTP  
  ▼  
AuditService (@Async + CircuitBreaker)  
  No bloquea el hilo principal  
  │  
  ▼  
MongoDB: colección audit-request 
 
2. Estrategias de auditoría (AuditStrategy) 
Configurable con audit.strategy en application.yml. 
NONE (por defecto) 
● No se captura nada. Cero overhead. 
ALL 
● Captura todas las llamadas WebClient (éxitos y errores). 
● Captura bodies de request y response.


--- [PÁGINA 70 DE 75] ---

ERROR 
● Solo captura bodies si hubo algún error (4xx/5xx o excepción). 
● Ideal para producción.

Componente Tipo

AuditContext. 
WebClientAuditInterceptor ExchangeFilterFunction — Intercepta cada llamada WebClient.

AuditService @Service + @Async — Persiste en MongoDB.

9. Circuit Breaker 
Protege MongoDB de sobrecarga. 
failureRateThreshold:          50%  
slidingWindowSize:             10
